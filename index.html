START
A release owner defines a set of up to eight independent tasks and the acceptance criteria for the combined release.TARGET OPERATING MODEL
NON-NEGOTIABLE RULE

Development happens in parallel, integration happens on Staging, and Production receives one combined release. Staging does not promote PRs individually—it proves and promotes the final release artifact that contains them.

  1. 01
    HUMANRelease owner
    Release scope

    Define the intended tasks, owners, dependencies and combined acceptance criteria.

    OUTPUT

    A controlled release batch containing up to eight independently deliverable tasks.

  2. 02
    HUMANEight engineers / agents
    Eight branches + worktrees

    Work on the tasks concurrently. Every task remains isolated from the other working copies.

    Task 1Task 2Task 3Task 4Task 5Task 6Task 7Task 8
    OUTPUT

    Up to eight independent change streams; no shared Development branch is used.

  3. 03
    AUTOMATICGitHub + CI + Coolify
    Draft PRs → Development VPS

    Each Draft PR opening or branch push independently runs preflight and automatically creates or updates its own Development preview.

    OUTPUT

    Up to eight isolated Development URLs, each tied to its own PR number and commit SHA.

  4. 04
    DECISIONPer-PR decision
    Development previews

    Is each engineer satisfied with their deployed task?

    OUTPUT

    Each PR advances or loops independently; one failed task does not overwrite another task's preview.

    YES / PASS →

    That engineer marks only that Draft PR Ready for review and continues to Step 5.

    NO / FAIL ↩

    Repair that task's branch and push again. Its own preview redeploys; the other seven lanes continue.

  5. 05
    AUTOMATICGitHub + reviewers
    Ready PRs + full CI

    Run the complete required gates and human review separately for every Ready PR.

    OUTPUT

    Merge evidence for each exact PR SHA.

  6. 06
    DECISIONPer-PR merge decision
    Protected main

    Is this PR green, approved, current and safe to combine with what has already merged?

    OUTPUT

    Individual permission to merge or a return-to-branch loop.

    YES / PASS →

    Merge that PR into main. The main commit now includes it and all earlier accepted PRs.

    NO / FAIL ↩

    Keep it out of main. Repair and re-review that PR; do not block unrelated Development lanes.

  7. 07
    AUTOMATICGitHub + Coolify
    Main → Permanent Staging

    Every successful merge automatically updates Staging. Staging therefore accumulates PR 1, then PRs 1–2, continuing until the planned accepted set is present.

    OUTPUT

    A running integration environment that exposes interactions between the merged changes.

  8. 08
    DECISIONRelease decision
    Release scope + main

    Are all PRs intended for this release merged and is the final Staging commit identified?

    OUTPUT

    A frozen release candidate boundary.

    YES / PASS →

    Freeze the final main SHA and continue to Step 9.

    NO / FAIL ↩

    Wait for remaining approved PRs or explicitly remove an unready PR from this release scope; never bypass its gates.

  9. 09
    AUTOMATICRelease workflow
    Registry + Staging

    Build and identify one immutable release image for the frozen final SHA, then ensure Staging runs that exact digest.

    OUTPUT

    One release candidate containing the complete accepted set of merged PRs.

  10. 10
    HUMANStaging test team
    Permanent Staging

    Perform detailed end-to-end, integration, data, authorization, visual and operational testing on the combined release.

    OUTPUT

    Evidence for the whole release, including interactions that isolated Development previews cannot prove.

  11. 11
    DECISIONStaging decision
    Combined release evidence

    Did the complete release pass detailed Staging testing?

    OUTPUT

    Promotion eligibility or a contained repair cycle.

    YES / PASS →

    Nominate this exact image digest for Production and continue to Step 12.

    NO / FAIL ↩

    Stop. Fix through a new branch and PR, merge it, create a new final SHA and repeat combined Staging testing.

  12. 12
    HUMANNamed approver
    Protected production control

    Review the complete Staging evidence and manually approve the nominated release digest.

    OUTPUT

    Recorded authority to promote one exact combined release.

  13. 13
    AUTOMATICCoolify + monitoring
    Production

    Deploy the same immutable digest without rebuilding; run smoke checks and observe Grafana, Kuma and ITAgent.

    OUTPUT

    The combined release is live with health evidence and a last-known-good rollback point.

  14. 14
    DECISIONProduction decision
    Live health evidence

    Is the combined release healthy during the agreed observation window?

    OUTPUT

    Release closure or controlled rollback.

    YES / PASS →

    Close the release and record its PR list, final SHA, digest, approver and result.

    NO / FAIL ↩

    Roll back the complete release, alert the team and repair through the normal branch-to-Staging path.

FINISHProduction runs one approved, immutable release containing the accepted PRs; the release record and rollback point are complete.
